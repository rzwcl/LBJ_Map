## 1. 当前主任务：614_0_0.mbn 的 RX 频率调谐入口定位

### 1.1 目标与环境

- 目标固件：614_0_0.mbn。
- 工具：Ghidra 12.1.4。
- Image base：0x10000。
- 已知块：
  - segment_2：可执行块，0x10000..0x26B62。
  - segment_3：已初始化的数据块，0x27000..0x2548A7。
  - EXTERNAL：0x255000..0x255143，未初始化。

### 1.2 重要地址与已经建立的关系

- get_signals_info：入口 0x259A4。
- 它在 0x259BC 计算 R18 的 PC 相对基址，静态算出的值是 0x254710。
- get_signals_info 六次调用同一个包装层 0x25F70，位置为：
  - 0x259F8
  - 0x25A10
  - 0x25A28
  - 0x25A40
  - 0x25A58
  - 0x25A70
- 包装层 0x25F70 的主要指令包括：
  - 0x25F70 call 0x24C00
  - 0x25F74 allocframe
  - 0x25F78 combine R17R16,R2,R3
  - 0x25F7C callr R0
  - 后面比较返回值并在需要时调用 0x24CF0，最后跳转 0x24C30。
- 因而目前能确认的是：六个调用点复用同一个间接调用包装层，调用前 R0 从表/基址相关位置装入不同的静态值。不能把 0x25F70 本身直接认定为 RF 调谐函数。
- R18=0x254710 时，六个调用点前读取 R0 的槽位与当前静态值是：
  - 0x2546B4 -> 0x25598，函数 get_instance，入口已识别。
  - 0x2546B8 -> 0x25604，函数 get_instance，入口已识别。
  - 0x2546BC -> 0x25694，函数 get_instance，入口已识别。
  - 0x2546C0 -> 0x25700，函数 get_instance，入口已识别。
  - 0x2546C4 -> 0x27384，segment_3 数据区，当前不可执行且没有识别函数。
  - 0x2546C8 -> 0x217458，segment_3 数据区，当前不可执行且没有识别函数。
- 后两项与“R0 后面被 callr 调用”的静态形态有矛盾。不要直接断言程序真的会跳入数据；要继续核验表的含义、运行时重定位、Ghidra 对条目的识别，以及关联全局存储/对象初始化路径。
- 0x254710 很可能是一个 PLT/GOT/解析器相关的基址锚点，因为大量 PC 相对 add 算到这里，PLT 风格 stub 也通过附近槽位间接跳转；仍然不能据此声称已经把所有运行时目标解析成功。脚本明确提示静态值可能是重定位占位值或 thunk 目标。

### 1.3 关键纠错：六个所谓“代码指针”其实是错误字符串

早期 STRUCTURE-35/36 的输出把六个记录字段暂时称为 code_pointer。STRUCTURE-36/37 拿到原始字节后，已经纠正这个解释：

- 0x264D4 的字节以 72 66 63 5F 开头，即可读 ASCII 字符串 rfc_hwid614_qrm865ab_v3_ag_cmn_ag.cpp:RFC ERROR NR5G Data Object is NOT Created . Cannot operate...
- 0x26544 对应同一源文件里的 WCDMA Data Object is NOT Created 错误信息。
- 0x265B4 对应 CDMA 错误信息。
- 0x26624 对应 GSM 错误信息。
- 0x26694 对应 TDSCDMA 错误信息。
- 0x26708 对应 GNSS 错误信息。
- 六个地址虽然位于 executable 的 segment_2 内，但 listing 在这些地址均没有指令、没有函数、也没有入向代码交叉引用；原始 48 字节全部是错误字符串文本，不是机器码。
- 所以这些地址绝不能继续当作函数入口分析，也不能因它们落在 executable block 就反汇编或认作调谐代码。
- 这些错误信息对应的记录位于 0x272C0..0x272FC，表面结构是每条 12 字节：
  - 0x272C0：field0=0x264D4（NR5G 错误字符串），field1=0xE06D3，field2=8。
  - 0x272CC：field0=0x26544（WCDMA 错误字符串），field1=0xE06DD，field2=8。
  - 0x272D8：field0=0x265B4（CDMA 错误字符串），field1=0xE06E7，field2=8。
  - 0x272E4：field0=0x26624（GSM 错误字符串），field1=0xE06F1，field2=8。
  - 0x272F0：field0=0x26694（TDSCDMA 错误字符串），field1=0xE06FC，field2=8。
  - 0x272FC：field0=0x26708（GNSS 错误字符串），field1=0xE0B7B，field2=8。
- 应将它们视作“包含错误消息指针、数据指针/字段、长度值的记录”的候选表；具体 C/C++ 结构体语义还没完全证实。

## 4. 补充历史里的设备独立 ID 研究：不要把车头型号/车号当作发射器 ID

用户明确纠正过：POCSAG 地址 1234002 所携带的是车头型号与机车车号信息，例如 HXD1C-0615 / HXD1C-0605；它不是用户怀疑的 ID。用户要找的是车载综合电台/发射装置本体自己的独立 ID。

历史记录提到的采集：
- 20866：对应 HXD1C-0615。
- 40042：对应 HXD1C-0605。
- 821 MHz IQ 文件包括 train_unknown_821.2367MHz_20261006_004707.iq（历史记录称约 12.3 MB）、train_unknown_821.2371MHz_20261006_010249.iq，以及 20866 的 004724.iq 等；40042 目录曾显示有 5 个 IQ 文件和 JSON。部分早期步骤只是确认网盘上文件存在、可触发下载，不能把“网页端能访问”说成模型已经拿到二进制；后续历史记录则记载两份 821.237x MHz IQ 已被上传并进行过 POCSAG 全地址扫描。后续对话应按实际附件/日志核实文件是否可用。
- 一份专利 PDF 名称为《发明专利申请（列车综合预警系统及其方法）》。历史对话将其作为待核实的架构线索：821.2375 MHz 一侧是 POCSAG 广播，866.2375 MHz 一侧涉及 FFSK/车载综合电台通信。需要重新打开专利原件核实具体参数，不能只把摘要里的频点当成当前实测事实。

已记载的 821 MHz 全 RIC 扫描结论：
- 20866 的有效 POCSAG 区间：Sync -> 1234000-F3 -> 1234002-F3 -> Idle；地址码字记录为 4B515A86。
- 40042 结构相同；其 1234002 地址码字有 1 bit 错误，原始记为 4B51DA86，BCH 纠正后为 4B515A86。
- 同一段有效 POCSAG（Sync 到 Idle）没有发现额外 RIC 作为第三个“发射器 ID”。
- 共同出现的 154250-F3 不能被认作每台发射装置的独立 ID，因为两辆不同车都有该值；还要注意原始记录中的 frame-position/地址解释，若要再用需回看相应解码日志。
- 因此，现有 821 MHz 结果可以排除“在这两份已扫描的 LBJ POCSAG 消息里额外插入第三个 RIC 作为设备 ID”这种简单假设；它不能证明全系统不存在设备 ID。
- 用户已确认 Function 对方向的解释是 F1=下行、F3=上行。后续车次关联逻辑要把 function 作为强约束，不要主要依靠公里标增减来猜方向，公里标只能作为辅助一致性校验。
- 接下来最值得做的采集是 866.2375 MHz（或经专利/设备资料确认的相应 FFSK 频道）的原始 IQ。821 MHz IQ 不能用来直接分析另一频点上的通信内容。也可以对同车多份 IQ 按 POCSAG 前导第一个有效符号对齐，比较前导前 100–300 ms 的 RF/IQ 活动：同一设备多次应有稳定共性，不同设备应可重复区分；当前“前导前弱 RF 活动”只是线索，尚非 ID 证据。
- 要寻找真实的设备独立 ID，应区分：机车/车辆信息（1234002）、LBJ 公共业务地址（如 154250）和车载发射器/综合电台自身身份。三者不是一回事。

## 5. POCSAG 串车问题：已锁定的软件层方向

历史文件分析了 RailwayPagerDemod、SX1276_Receive_LBJ 与 APK 的消息处理。核心问题不是简单的车型字典，而是 demod 端可能丢掉 POCSAG message boundary，业务层再用全局最近车次或字符串判断，导致多车交错时把不同 Address 的内容拼到一起。

记录里指出的现有问题形态：
- demod.cpp 维护全局 address 与 numeric_msg。
- 每收到一个 32-bit codeword 就可能输出一次；新 Address 会覆写 address 并清空 numeric_msg。
- Java/Kotlin 再用字符串包含 1234000 / 1234002 判断消息类别。
- 这样会丢失同一个 POCSAG batch 的空中顺序、Address、Function、frame position 等关系。

建议的明确改造路线：
- 保留已工作的 IQ -> FSK 解调 -> POCSAG 同步 -> BCH 纠错。
- 优先只改 demod.cpp 中 decodeBatch()/processOneSample() 的消息边界处理与 decodeMessage.cpp 的输出/解析接口；别把 SX1276 硬件驱动照搬进 Android。
- 增加完整消息组装器：按连续 codeword 顺序收集消息，在下一个 Address 或 Idle 等真正边界到来时关闭上一条；使用结构化字段 address、function、framePos、burstId、payload，而不是全局字符串状态。
- 完整消息交给 LBJ 解析层后，再按同一 burst/message 的上下文配对 1234000（动态列车数据）与 1234002（车型/机车号数据）。不要跨任意相邻消息直接拼接，也不要依靠“最后收到的车次”全局变量。
- 如果两辆车的同频发射真正同时、互相破坏并只形成无法纠错的一串比特，接收端软件无法凭空恢复每个 bit 属于哪辆车；但对于分时、可完整解码的多车广播，正确保留 POCSAG batch/address/message boundary 可以避免软件层造成的许多串车。
