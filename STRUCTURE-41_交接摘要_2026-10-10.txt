# STRUCTURE-41 交接摘要（2026-10-10）

## 0. 当前最高优先级：修正 Hexagon PC-relative 的基准

当前任务仍是只读静态分析 Qualcomm `614_0_0.mbn`，找到真实 RX 频率调谐调用链。目标 Ghidra Program Image Base 为 `0x10000`。不要混用旧 `qdsp6sw.mbn` 的 C8/C9 地址。

**重要纠正：STRUCTURE-39 的“8 个访问点全部匹配”结论无效。** 该版本错误地把 Hexagon PC-relative 地址计算为 `add_address + instruction_length + immediate`，随后又拿由同一错误公式推导的预期地址进行匹配，形成了循环验证。

Qualcomm Hexagon V73 Programmer's Reference Manual 的 “Add to PC” 章节（印刷页 197）说明：PC-relative immediate 要加到当前 instruction packet 的起始地址上，而非 add 指令结束地址。参考页：
- https://device.report/m/9617176bfefffcbc1efdcc55512335e567e0d9a1c8a2813a1538de55ed99cf3b.pdf
- HTML 提取文本中说明 PC 是 packet start：可在 https://device.report/m/9617176bfefffcbc1efdcc55512335e567e0d9a1c8a2813a1538de55ed99cf3b 中查 “The PC value is the address of the start of the packet”。

因此，此前所有以 `ins.getAddress().getOffset() + ins.getLength() + displacement` 推导出的 614_0_0 PC-relative 候选都必须重新核实。这包括 R18 基址、六个 getter pointer slot、RFC anchor、PC-relative data target 和 PLT/GOT slot。**当前不要再把旧日志中 R18=0x254710、旧六个 R18 槽位以及旧 PLT/GOT 槽位当作确认的实际地址。**

## 2. 针对四个 getter 的正确候选地址（尚需新日志核对）

四个已知 getter 的 PC-relative `add` 均由前一条 `immext` 扩展，PC packet start 应为 `immext` 地址。以当前 Listing 文本计算：

| Getter | Packet start + immediate | memw displacement | 候选 singleton slot |
|---|---|---|---|
| `0x25598` | `0x25598 + 0x22F170 = 0x254708` | `-0x8C` | `0x25467C` |
| `0x25604` | `0x25604 + 0x22F104 = 0x254708` | `-0x84` | `0x254684` |
| `0x25694` | `0x25694 + 0x22F074 = 0x254708` | `-0x18` | `0x2546F0` |
| `0x25700` | `0x25700 + 0x22F008 = 0x254708` | `-0x10` | `0x2546F8` |

这些是按 packet-start 语义重新计算的候选，并非运行时重定位后的最终对象地址。STRUCTURE-41 会读取这些槽位的静态内容并同时打印 Ghidra 保存的引用；下一步必须通过新日志核实。

- 不能声称找到 RX tune 入口。目前还没有证据确认具体函数执行频率编程或调用 RF driver。
