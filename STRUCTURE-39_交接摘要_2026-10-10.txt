## 2. STRUCTURE-38 新发现（以日志为准）

四个单例槽方法打印的静态值：

- `0x254684 -> 0x255040`，目标块 EXTERNAL；
- `0x25468C -> 0x254888`，目标块 segment_3；
- `0x2546F8 -> 0x255070`，目标块 EXTERNAL；
- `0x254700 -> 0x21743C`，目标块 segment_3。

这些静态值不说明槽位访问地址计算错误；它们是槽内容，不是 getter 访问地址。还要区分静态值是否为重定位占位值。

日志列出的 Ghidra 引用存在需要验证的不一致：

- 对候选槽 `0x254684`，打印的引用来自 `0x25614` 和 `0x25630`。
- 对候选槽 `0x25468C`，打印的引用来自 `0x25688`。
- 对候选槽 `0x2546F8`，打印的引用来自 `0x25710` 和 `0x2572C`。
- 对候选槽 `0x254700`，打印的引用来自 `0x25780`。

而 listing 的 PC-relative add 与 memw displacement 按公式计算，应当是：

- `0x2559C + 4 + 0x22F170 = 0x254710`；`0x254710 - 0x8C = 0x254684`。Getter `0x25598` 的两个候选访问位置是 `0x255A8` 和 `0x255C4`。
- `0x25608 + 4 + 0x22F104 = 0x254710`；`0x254710 - 0x84 = 0x25468C`。Getter `0x25604` 的两个候选访问位置是 `0x25614` 和 `0x25630`。
- `0x25698 + 4 + 0x22F074 = 0x254710`；`0x254710 - 0x18 = 0x2546F8`。Getter `0x25694` 的两个候选访问位置是 `0x256A4` 和 `0x256C0`。
- `0x25704 + 4 + 0x22F008 = 0x254710`；`0x254710 - 0x10 = 0x254700`。Getter `0x25700` 的两个候选访问位置是 `0x25710` 和 `0x2572C`。

这些计算与源码中此前采用的 PC-relative 基址计算方式一致，但下一版运行输出仍要以 Ghidra 实际 instruction operands 为准。Ghidra reference manager 的既存 xref 不能单独充当运行时有效地址的权威证据。

## 3. STRUCTURE-39 新增审计做什么

新方法 `scan614RfcGetterEffectiveSlotAudit()` 仅针对上述四个 getter：

- 读取 listing 中现有 PC-relative add 指令和两个 memw 访问指令；
- 从 Scalar 取得实际显示的立即数字段，重新计算 PC-after + displacement 得到基址，再加 memw 位移得到 effective address；
- 每个计算地址与预期槽位逐条比较；
- 单独打印 Ghidra 已存储的引用以及它们是否从当前 memw 指令直接指向计算出的地址；
- 最后汇总 getter 数、访问点数、预期槽位匹配数、存储引用匹配数以及取不到指令/立即数的数量。

新输出标记：

- `614_RFC_EFFECTIVE_AUDIT_GETTER`
- `614_RFC_EFFECTIVE_AUDIT_PC_BASE`
- `614_RFC_EFFECTIVE_AUDIT_ACCESS`
- `614_RFC_EFFECTIVE_AUDIT_EXISTING_REF`
- `614_RFC_EFFECTIVE_AUDIT_GETTERS_INSPECTED`
- `614_RFC_EFFECTIVE_AUDIT_ACCESS_SITES_INSPECTED`
- `614_RFC_EFFECTIVE_AUDIT_EXPECTED_SLOT_MATCHES`
- `614_RFC_EFFECTIVE_AUDIT_STORED_DIRECT_REFERENCE_MATCHES`
- `614_RFC_EFFECTIVE_AUDIT_MISSING_INSTRUCTIONS_OR_IMMEDIATES`

这版未在本地 Ghidra 编译或运行。用户下一步下载最新脚本，覆盖原脚本路径 `D:\\X55RE\\ghidra_scripts\\Ghidra_RFDEBUG_Trace.java`，在同一个 `614_0_0.mbn` Program 中运行，随后将日志另存并读取输出。

## 4. 为什么不能把四个二级调用目标直接当构造函数

STRUCTURE-38 日志中的下列地址均显示为 PLT/GOT 式间接跳转桩：

- `0x24C80` -> 槽 `0x254750`，静态值 `0x25564`；
- `0x24CB0` -> 槽 `0x25475C`，静态值 `0x255030`；
- `0x24E90` -> 槽 `0x2547D4`，静态值 `0x2573C`；
- `0x24EB0` -> 槽 `0x2547DC`，静态值 `0x25F38`。

其指令形态包括从 PC 相对槽读入 R28、再执行 `jumpr R28`。某些静态目标与 Ghidra 显示的标签不一致；必须核对装载/重定位语义，不能因标签是 RFC 类符号就宣布它们是构造函数实现。

共享 helper `0x2526C` 的输出为两条指令，之后跳向 `0x24BE0`，在 PLT/GOT 静态映射里该入口被标记为 `operator.new`。这与分配包装器一致，但因跳转槽静态值存在不确定性，仍须验证真实目标。

## 5. 当前已确认 / 尚未确认

已确认：

- `get_signals_info` 位于 `0x259A4`，六个 callsite 都汇聚到 `0x25F70`，其间接调用指令是 `0x25F7C: callr R0`。
- `0x254710` 是大量 PC-relative 计算得到的基址候选。
- 六个所谓“代码指针” `0x264D4`、`0x26544`、`0x265B4`、`0x26624`、`0x26694`、`0x26708` 实际是 RFC 错误字符串，不是函数入口。
- STRUCTURE-37 静态数据区扫描记录 570,922 个 word、14 个匹配；该结果用于确认数据引用，不是调谐入口证据。

尚未确认：

- 单例槽静态值的真实运行时语义与重定位结果；
- 四个二级调用目标的最终运行时目标；
- 当前 RFC 配置查询与真正 RX 频率设置之间的调用链；
- RX tune 函数入口。

禁止将配置查询符号名、executable block 标志、Ghidra 已有 xref 或静态指针槽值单独当成实际调谐证据。

## 7. 下一步的唯一优先任务

先运行 STRUCTURE-39 定向有效地址审计。对输出逐项核对：

1. PC-relative base 是否都计算为 `0x254710`；
2. 每两个 memw 的 effective address 是否各自都指向同一候选 slot；
3. Ghidra 的 stored direct reference 是否真的从当前访问指令指向 computed address；
4. 是否有指令/立即数解析失败。

根据这轮输出决定接下来是修正引用解释、检查程序分析状态，还是进一步追踪单例对象的创建路径。没有这些证据之前，不追加无目标的全域扫描，也不称已找到 RX 调谐入口。
